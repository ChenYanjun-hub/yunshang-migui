> 「我先放一张图。」（打开首页）
> 
> 「这是云上米轨。一个把『滇越铁路 855 公里、120 年』装进浏览器的垂直知识服务平台。
> 
> 我们不是在做一个铁路博物馆官网，也不是在做一个通用 AI 问答。我们在做的是——**让一个普通人，能像策展人一样，看懂这条铁路。**」

**为什么这么开**：一句话定位 + 一个反差（不是通用、不是官网），让听众立刻明白这是「窄而深」的产品。

## 3 · 架构总览（90 秒）

**Slide 建议画一张三层图**：

```
┌─────────────────────────────────────────────────────────┐
│ Presentation 层                                          │
│ Next.js 16 (App Router · React 19 · Tailwind v4)        │
│ ├─ 7 用户端模块  ├─ Admin 后台（5 角色）  ├─ Proxy 鉴权 │
└─────────────────────┬───────────────────────────────────┘
                      │ Server Actions / RSC
                      ▼
┌─────────────────────────────────────────────────────────┐
│ AI 层 · 南渡 RAG                                         │
│ ┌──────────────┐ ┌──────────────┐ ┌──────────────────┐ │
│ │ Embed        │ │ Retrieve     │ │ Generate         │ │
│ │ DashScope    │→│ pgvector     │→│ DeepSeek         │ │
│ │ text-emb-v3  │ │ cosine top-K │ │ deepseek-chat    │ │
│ │ 1024 维      │ │              │ │ (AI SDK v6)      │ │
│ └──────────────┘ └──────────────┘ └──────────────────┘ │
└─────────────────────┬───────────────────────────────────┘
                      ▼
┌─────────────────────────────────────────────────────────┐
│ Data 层 · Supabase                                       │
│ ├─ Postgres + pgvector （档案 · 嵌入 · 社区 · 商品）    │
│ ├─ Auth （邮箱/手机 · 6 角色 · RLS 行级隔离）           │
│ └─ Storage （图片 · 字体 · 文件）                       │
└─────────────────────────────────────────────────────────┘
```

**口述**（90 秒）：

> 「三层结构，自上而下讲。
> 
> **最上层是表现层**——Next.js 16 + React 19 + Tailwind v4。这里有 7 个用户端模块、一个 Admin 后台、一套基于 proxy.ts 的鉴权链。
> 
> **中间是 AI 层**，也就是我们叫『南渡』的 RAG 系统。三步：embedding 用阿里 DashScope 的 text-embedding-v3，1024 维；检索靠 Postgres 的 pgvector 扩展，余弦相似度取 top-K；生成走 DeepSeek 的 deepseek-chat，通过 AI SDK v6 调用——这个 SDK 帮我们处理流式响应、re-generate、tool 调用，省了不少 glue code。
> 
> **底层是 Supabase 一站式后端**：Postgres 当 OLTP 库，pgvector 当向量库，Auth 处理 6 种角色，RLS 做行级权限隔离。Storage 放图片、字体、附件。
> 
> 选 Supabase 的关键原因不是它『免费』，而是它让我们一个人能管完整后端——开发期 PM + 1 名工程师就能跑。」

**关键替换台词**（如果听众是技术深的人）：

- 「pgvector 比单独的向量库（Pinecone/Weaviate）的好处是事务、备份、权限和业务数据走一套——RAG 系统里数据治理才是大坑，统一一个库省一半运维」
- 「DashScope 选 v3 而不是 v4 的原因：v4 维度更高但中文语义提升对我们语料增益小，向量存储和查询成本翻倍不划算——这种选型记在 Decision Notes 里」

## 🧯 Q&A 预案（讲完 6 分钟后留 1.5 分钟）

我估三个最可能被问的：

**Q1：「凭什么我们做的 RAG 比直接用 ChatGPT 强？」**

A：通用 LLM 没读过你的内部档案，遇到「五家寨大桥钢拱跨度多少」这种问题，要么答错要么编。我们的 RAG 让 LLM 看到真的档案再答，并标来源——一旦评委追问出处，能现场打开档案对照。这是文化领域刚需。

**Q2：「Supabase 这种『一站式』选型，万一被锁死怎么办？」**

A：底层是开源 Postgres + pgvector，迁移路径是有的——`pg_dump` + 自建 Postgres 即可。我们用的 Supabase 能力都是标准 SQL / RLS / OAuth 的范畴，没有专有 API 锁。前期换更轻的栈是错的——它让我一个人能管完整后端，节省的人力比迁移风险大。

**Q3：「字体（京華老宋体）有版权风险吗？」**

A：开源字体，许可允许商用。我们做了本地子集化（999 字 / 776KB），不依赖第三方 CDN，部署完全自有。Decision Notes 里有详细记录。
