# 一 · AI 与 RAG 架构

## 决策 #1 · RAG vs Fine-tune vs Plain Prompt

**问题**：南渡 AI 要回答滇越铁路专业问题。三条路怎么选？

**候选**：
- A. **Plain Prompt** — 写好 system prompt，让 LLM 凭训练知识答
- B. **Fine-tune** — 用项目史料微调专属模型
- C. **RAG** — 史料入向量库，每次提问检索后拼 prompt

**选择**：**C · RAG**（2026-05-06 锁定）

**理由**：
1. **专业领域**：滇越铁路在通用 LLM 训练数据中占比极小，Plain Prompt 必幻觉
2. **可追溯**：博物馆级项目，"史料从哪来"是核心要求，RAG 天然带 citation
3. **新增成本**：admin 上传一条新档案跑一遍 embed 就生效，Fine-tune 要重训
4. **预算**：RAG 无训练成本，只有 embedding（一次性）+ LLM 推理（按 token）

**实际效果**：CitationStrip 直接呈现源出处，评审追问"这一句话哪来的"能现场点开档案。Demo 一致正面反馈。

**可逆性**：**易切换**。把 retrieve 调用屏蔽掉就退回 Plain Prompt；Fine-tune 升级不影响 RAG 已有数据。

## 决策 #2 · Embedding 模型 — DashScope text-embedding-v3

**问题**：选哪个 embedding 模型把档案变成向量？

**候选**：
- A. OpenAI text-embedding-3-small（1536 维）— 业界标杆但要 VPN
- B. DashScope text-embedding-**v3**（1024 维）— 阿里通义，国内直连
- C. DashScope text-embedding-**v4**（1024-2048 可选）— v3 的升级版，中文略好

**选择**：**B · DashScope v3**（2026-05-11 落地）

**理由**：
1. **国内可用**：v3 国内直连，符合"演示零代理依赖"
2. **维度 vs 成本**：1024 维查询向量存储成本只有 OpenAI 的 66%，对窄领域语料检索质量足够
3. **v3 vs v4**：v4 维度更高，但对小规模 (~100 档案) 提升边际有限，向量存储和查询成本翻倍不划算
4. **跟 LLM 同生态**：DashScope 体系跟项目其他阿里能力（如来日的 OSS 存储、短信）打通容易

**实际效果**：18 条档案全部嵌入，HNSW 索引下检索 < 50ms，余弦相似度 0.5+ 命中率 100%。

**可逆性**：**中等**。换模型要重跑 embed（一次性几分钟）+ 调阈值。已留 `embedding_model` 字段做多模型并存的能力，但目前没用上。

## 决策 #3 · LLM 选 DeepSeek 不选 Claude/GPT

**问题**：生成阶段用哪个 LLM？

**候选**：
- A. OpenAI gpt-4 / Claude 3.5 Sonnet — 顶级智能 + 要 VPN + 贵
- B. DeepSeek deepseek-chat — 国内可用 + 便宜（约 1/10 OpenAI 价）+ 中文好
- C. 阿里通义千问 qwen-max — 国内 + 跟 DashScope 同家

**选择**：**B · DeepSeek deepseek-chat**（2026-05-10 锁定）

**理由**：
1. **零代理**：国内直连，演示绝不能依赖 VPN
2. **中文质量**：在文化遗产、史料解读这种语境下，DeepSeek 表现已超 GPT-3.5，接近 GPT-4
3. **成本**：~¥0.001/千 token 输出，演示阶段月 < ¥10
4. **流式 + tool calling 完备**：通过 `@ai-sdk/openai-compatible` 适配，AI SDK v6 全套能力都能用
5. **vs 通义**：通义生态绑定深一些（万一未来要换数据库），DeepSeek 更"中性"

**实际效果**：流式响应 700ms 内首字，2-4 秒完整答复。CitationStrip 配合的引用语义还原度高。

**可逆性**：**很易**。`@ai-sdk/openai-compatible` 接口统一，换 LLM 改 1 个 env 变量 + 1 行 model 名。

## 决策 #4 · 检索 threshold 0.30 → 0.40

**问题**：余弦相似度阈值定多少？

**背景**：5/12 测试时观察到脱题 query「如何用 Rust 写一个 TCP 服务器？」会硬召回 1 条 sim 0.342 的噪声（人字桥工程图纸）。模型靠 system prompt 第 4 条扛住没乱讲，但前端 CitationStrip 仍渲染了那条无关史料 — UX 不优雅。

**选择**：**threshold 0.30 → 0.40**（2026-05-13）

**理由**：
- 0.30 太宽容，会把"维度勉强相关"的噪声放进 prompt 当上下文，污染回答
- 0.40 测试：5 条正常 query 全过（最低 0.519），脱题 Rust query 0 召回 — 干净切除噪声
- 没有引入新 bug：正常 query 召回数变化 < 5%

**实际效果**：脱题问题不再渲染无关引用条，演示安全感大幅提升。

**可逆性**：**极易**。`retrieve.ts` RetrieveOptions 默认值 + chat route 显式传值，2 处都改。未来如果增加 PDF 长文档（chunk 增多）可能要回调到 0.35。

**留痕**：这是 "调一个参数解决一类异常" 的便宜事，能做就做。

# 二 · 平台与数据

## 决策 #5 · Supabase 一站式 vs 自建后端

**问题**：后端怎么搭？

**候选**：
- A. **Supabase**（Postgres + Auth + Storage + Realtime + Vector + RLS 一站式）
- B. **自建 Node + Postgres + S3 + 自写 Auth** — 灵活但工作量大
- C. **Firebase** — Google 系，国内访问慢

**选择**：**A · Supabase**（2026-05-06 锁定）

**理由**：
1. **一人能管**：PM 同时是开发，自建后端的 ops 成本受不了
2. **pgvector 内置**：标准 Postgres 扩展，不用单独的 Pinecone/Weaviate 增加运维面
3. **RLS 行级权限**：业务逻辑写在 SQL 里，应用代码不用反复手写权限判断
4. **Auth 含 5+ 第三方登录**：邮箱/手机/OAuth 全部内置
5. **开源底层**：Supabase 本质是包装的开源 Postgres，未来迁移路径 `pg_dump` 即可

**实际效果**：从 5/7 到 5/20，0 后端 ops 工时。每天专注前端 + RAG + 设计。

**可逆性**：**中等**。Postgres 数据可 dump 走，Auth 数据需要写迁移脚本，Storage 文件要重新上传。一周内可以迁移到自建/阿里云 Postgres。

**长期风险**：Supabase 在新加坡（我们 Region），国内浏览器直连有 80-150ms 延迟。Phase 3 如果要正式运营，考虑迁阿里云 RDS Postgres + 自建 Auth。

## 决策 #6 · 向量库 — pgvector vs 独立向量库

**问题**：向量数据放哪？

**候选**：
- A. **pgvector**（Postgres 扩展，跟主库同实例）
- B. **Pinecone / Weaviate / Milvus**（独立专用向量库）
- C. **本地内存**（faiss，不持久化）

**选择**：**A · pgvector**（2026-05-11 落地，HNSW 索引）

**理由**：
1. **事务一致性**：档案 + 向量在同一个事务里写，永不出现"档案有了但向量没建"的中间态
2. **统一备份**：`pg_dump` 一把抓所有数据，不用维护两套备份策略
3. **统一权限**：RLS 同时管理档案和向量的读写权限
4. **运维面减半**：少一个外部依赖 = 少一个故障点 = 少一个监控告警
5. **性能足够**：HNSW 索引下 100K 向量级别查询 < 50ms，演示规模 (~100 条) 完全无感

**实际效果**：从开通到能查 < 2 小时（Supabase Dashboard 一键 enable extension）。0 运维成本。

**可逆性**：**中等偏易**。向量数据可以 `pg_dump` 导出后导入到独立向量库（用 Pinecone/Weaviate 的 client 批量写入）。schema 解耦，应用层换 retrieve 实现即可。

**关键场景外的考虑**：如果未来上到百万级档案 + 高并发查询，pgvector 可能扛不住，要考虑专用向量库。但 Phase 3 仍在演示+早期运营，远未到该量级。

# 三 · 设计语言与品牌

## 决策 #7 · 视觉风格切换 — 风格 C → 风格 B

**问题**：项目视觉语言定哪种？

**候选**（5/4 探索的 3 个方向）：
- A. **博物馆官方风** — 严肃、对称、深红/深蓝主色
- B. **cinematic editorial 风** — cream-on-cream + 朱砂点缀 + 大量留白 + 京華老宋体
- C. **科技未来感** — 深色背景 + 霓虹蓝 + sci-fi 字体

**选择**：**B**（2026-05-04 由 C 切换到 B）

**理由**：
1. **品类差异化**：A 是博物馆官网的标准答案，做出来跟既有产品同质；C 跟"文化遗产"气质冲突，年轻太重
2. **比喻一致性**：滇越铁路是 1903 年法方修建的窄轨铁路，B 风格的 cream + 朱砂 + 衬线字体跟那个时代的"档案 + 印章"语言天然吻合
3. **慢阅读引导**：cream-on-cream 低对比迫使用户慢下来读，符合"博物馆级内容"定位
4. **风格独占**：在国内类似项目里，B 风格几乎找不到第二个，是产品独特记忆点

**实际效果**：5/19 桌面 1440 通走 9 页 0 视觉 bug。用户测试反馈"打开就感觉这是个正经的文化产品"。

**可逆性**：**很难**。整套设计 token、字体、组件库都按 B 实施，回切要重做。**因此这是 Phase 1 早期就锁死的决策，避免后期反悔代价**。

**踩坑**：5/15 Exhibition β 用 GSAP pin scroll 试图加"沉浸感"，立刻被用户判定"垂直/横向冲突" — pin scroll 是 SaaS landing page 的语言，跟 B 风格的"档案 / 史料 / 长卷" 比喻冲突。返工见决策 #9。

## 决策 #8 · 字体 — 京華老宋体本地子集化

**问题**：项目中文衬线字体用什么？

**候选**：
- A. **思源宋体 Noto Serif SC**（Google Fonts CDN）— 免费但国内 CDN 慢/被墙
- B. **方正/汉仪商业字体**（CDN 或本地）— 设计感强但要付费
- C. **京華老宋体本地子集化** — 开源、复古书卷气

**选择**：**C · 京華老宋体本地子集化**（2026-05-17 落地）

**理由**：
1. **气质对**：京華老宋体是仿清末民初铅排活字风格，跟滇越铁路 1903 年的时代感强吻合
2. **免费可商用**：SIL 开源协议，长期运营无版权风险
3. **本地化部署**：自己 host woff2，零外部 CDN 依赖，演示绝不会因 GFW 拉不到字体而 fallback 到难看的黑体
4. **子集化**：用 pyftsubset 提取项目静态文本里的 999 字（CJK 850 + ASCII + 标点），单文件 776KB，加载快

**实际效果**：5/19 9 页全验证 h1/h2/h3 都正确使用 KingHwaOldSong，0 fallback 漏字。woff2 200 OK 加载稳定。

**可逆性**：**易**。字体绑定在 `--font-serif` CSS 变量，改一行即可换字体；本地文件可以补充字符或换基底。

**踩坑**：
- 早期尝试 cn-font-split（Node 工具）在 macOS Node 24 上的 koffi 库 bug 装不上 → 切 pyftsubset (Python 系) 一遍过
- 字体 family 名第一次写成 "Kinghwa OldSong"（空格 + 大小写错），实际正确是 "KingHwaOldSong"，bug 潜伏 8 天后才发现

# 四 · 模块技术选型

## 决策 #9 · Cloud Tour 地图栈 — 自渲染 SVG

**问题**：云游导览页的地图用什么实现？

**候选**：
- A. **Mapbox** — 顶级 GIS 库，瓦片美 + 交互流畅，但要 API key + 月度配额
- B. **Leaflet** — 开源主流，瓦片可自选，性能成熟
- C. **自渲染 SVG** — 把 GeoJSON 数据线性投影到 SVG viewBox 自己画

**选择**：**C · 自渲染 SVG**（2026-05-15 落地）

**理由**（这是 PM 视角而非工程便利的决策）：
1. **叙事差异化**：A/B 是"我用了主流 GIS 库"，C 是"地图本身就是一件档案" — 后者跟项目"博物馆级"定位深度契合
2. **风格统一**：SVG 可以完全应用项目朱砂 + cream 配色 + 衬线字体，不被瓦片色调污染
3. **零外部依赖**：演示不依赖 Mapbox/Leaflet 的 CDN 是否被墙
4. **小数据集合适**：MVP 32 站，跨度小（约 2.5° 纬度 × 1.3° 经度），10 行线性投影就够，墨卡托畸变可忽略

**实际效果**：5/19 walkthrough 验证 1440×900 full-screen SVG 渲染流畅，15 站点可点击。

**可逆性**：**中等**。组件接口 `<MiguiMap />` 已封装，未来要换 Mapbox 只改组件内部不影响调用方。

**留尾**：32 站点真实经纬度清单待队友提供；到位后改 `src/data/migui-line.ts` 一个文件，组件 0 改动。

## 决策 #10 · Exhibition 横向画卷 — 砍 GSAP pin scroll

**问题**：光影展览页的展厅效果怎么做？

**候选**（5/15 探索）：
- A. **CSS 卡片悬浮** — 简单但平凡
- B. **GSAP ScrollTrigger pin scroll** — "走进展厅"垂直转横向沉浸感
- C. **OGL 真 3D** — three.js 类，最炫但工程大
- D. **CSS perspective grid 错位** — 静态画面有空间感

**选择**：**B → 返工到 横向 scroll-snap**（2026-05-15）

**初选 B 的理由**：GSAP pin scroll 在 SaaS landing page 上是 教科书技术，被业界用 N 次，看起来稳

**返工原因**：实测 5 分钟后用户判定"垂直/横向冲突"。pin 的本质是"劫持垂直滚动转横向动画"，对"想快速浏览"的人极其反人类。

**最终选**：`overflow-x-auto + scroll-snap-type: x mandatory`
- 垂直滚动归页面、横向滚动归画卷，各管各
- "画卷"语义跟项目"档案/史料/长卷"的核心比喻一致

**实际效果**：用户体验从"被劫持"变成"自然翻阅"，符合"看展览"的真实动作。

**领悟**：动手前问一句 "这个交互的核心比喻是什么"。**比喻对了，技术选择就清楚了**。GSAP pin scroll 的比喻是 "电影感推镜"，跟米轨的"翻档案"是两个世界。

**可逆性**：**易**。CSS 改个 class 即可。

# 五 · 用户与权限

## 决策 #11 · 6 角色权限矩阵 + Supabase RLS

**问题**：项目要演示运营动作，用户角色怎么划分？

**候选**：
- A. **2 角色**（普通用户 + 单一 admin）— 简单但 demo 时讲不清"运营 vs 商务"区别
- B. **6 角色**（user + admin_product + admin_tech + admin_ops + admin_biz + super_admin）
- C. **基于 group 的灵活模型** — 工程上更优雅，但演示讲不出"我们考虑过组织架构"的故事

**选择**：**B · 6 角色**（Phase 1 后期定稿）

**理由**：
1. **演示叙事强**：5 个 admin 角色对应真实部门（产品/技术/运营/商务），评审一看就明白"这个系统是给一个有组织的团队用的"
2. **RLS 表达清晰**：每个 admin 子页通过 `profiles.role in (...)` 判断访问权限，SQL 即文档
3. **service_role bypass**：admin 实际写操作通过 service_role 绕过 RLS 直接写，但读视图仍走 RLS（最小权限）
4. **可扩展**：未来加 `admin_curator`（策展人）等新角色，只在 enum 加一行

**实际效果**：5/17 admin/community 实测 Hide/Show/Delete 鉴权链完整，未授权用户访问 admin 路由 307 重定向到登录页。

**可逆性**：**易**。`profiles.role` 是文本字段（不是 enum constraint），增删角色一行 SQL。

**约束**：
- 当前演示用户**手动种**（5/17 决策 #12 用户提到的"两个都成功了"指 002/003 migration 跑通）
- 真上线时要走 Supabase Auth 的注册流程 + admin 提权审核

# 六 · 部署运维

## 决策 #12 · 部署节点 — 阿里云东京

**问题**：5/23 demo 前要把项目部署到一个国内能稳定访问的地方

**候选**：
- A. **本地笔记本投影** — 0 部署风险，但依赖会议室 WiFi + 没法分享 URL
- B. **国内节点（阿里云杭州/上海）+ ICP 备案** — 延迟最低（<50ms）但备案要 5-20 工作日，**5/23 来不及**
- C. **阿里云香港轻量** — 免备案 + 国内 BGP 优化 + 50-100ms，但库存抢
- D. **阿里云新加坡轻量** — 免备案 + 100-200ms，库存通常充足
- E. **阿里云东京轻量** — 免备案 + Supabase 同机房（Region: Northeast Asia Tokyo）+ 100-200ms

**选择**：**E · 阿里云东京**（2026-05-20 落地）

**理由**：
1. **ICP 备案绝不可能**：5/23 deadline 距今 3 天，最快备案也要 5 工作日
2. **东京 vs 香港**：香港延迟略低（50-100ms），但东京 ECS 到 Supabase **同机房 <5ms**。Server Component 渲染时多次查 DB，省下的累计延迟比香港优势大
3. **东京 vs 新加坡**：东京到 Supabase 0 延迟，新加坡到 Supabase 仍要 80ms
4. **预算**：2核 2GB / 200Mbps / Ubuntu 24.04 = ¥56/月，1 个月 demo + 续费看运营情况

**实际效果**：5/20 13:00 完成部署，公网 IP `47.245.10.156`，浏览器访问首页 ~1.2s 加载，全链路（注册/登录/admin）端到端验证通过。

**架构**：
```
用户 → nginx :80 → pm2 → npm run start → next start :3000
                    ↑
              开机自启 + crash 自动重启
```

**可逆性**：**易**。代码是 Git 仓库，env 是 5 个 key，30 分钟内能在任何 Node 服务器上重建。

**留尾**：
- Phase 3 正式运营：跑 ICP 备案 + 迁国内节点（延迟从 ~100ms 压到 <50ms）
- 短期加固：换 SSH key 登录、关闭密码登录、配 HTTPS（Let's Encrypt）

# 附录 · 决策方法学

12 条决策回头看，3 个反复出现的模式：

### 1. "比喻一致性"是设计决策的最高判据
- 视觉风格 (B 风格 cream-on-cream) — 比喻是"档案 + 印章"
- Cloud Tour 自渲染 SVG — 比喻是"地图本身就是档案"
- Exhibition 横向 scroll-snap — 比喻是"翻阅长卷"
- 砍 GSAP pin scroll — 因为它的比喻是"电影推镜"，跟米轨冲突

> 动手前问 "这个交互的核心比喻是什么"。比喻对了，技术选择就清楚了。

### 2. 演示场景下，"零外部依赖"权重远高于"最佳工程实践"
- LLM 选 DeepSeek 不选 Claude — 因为 VPN 风险
- 地图自渲染 不用 Mapbox — 因为 Mapbox CDN 可能慢
- 字体本地子集化 不用 Google Fonts CDN — 因为 GFW
- 部署东京 不用 Vercel — 因为延迟不可控

> 演示是一次性的。一次失败的影响 > 三个月的代码债。

### 3. 跨模块影响要 "先列清单再动手"
- 5/15 admin/archives actions 漏了 revalidate /exhibition，导致 server component 看到旧数据
- 5/17 admin/community 真后台需要 service role bypass RLS，原本没注意
- 5/19 登录修复发现 `NEXT_REDIRECT` 信号被 `startTransition` 吞掉，跨边界问题

> 写 server action 时最后一步必须问：哪些路由读了这张表？我都 revalidate 了吗？
