### 2. AI 错误态 UI

**问题**：useChat status 变 'error' 时前端完全无反馈，用户不知道是发出去没、是不是该重试。

**实现**
- 在 [src/app/ai/AIChatClient.tsx](../src/app/ai/AIChatClient.tsx) 解构 `error / regenerate / clearError`
- 新组件 `ErrorBanner`：朱砂左边线 + `bg-cinnabar-soft` 底 + 印章式打字机字头 `TRANSMISSION ERROR · 信号中断` + 错误消息（截断 240 字防长 stack 溢出）+ `btn-seal` 重试按钮 + 弱化的关闭按钮 + 240ms 入场动画（复用 Lightbox 的 `lightbox-in` keyframe）
- 渲染位置：消息流末尾、`ml-12` 与 assistant 头像缩进对齐（不抢 sticky header）
- `submit()` 增加 `if (error) clearError()` 兜底，用户主动改写问题重发时清掉旧错误条
- `handleRetry()` **智能分支**：
  - 最后一条是 user（请求未到达模型就 error）→ 提取 text → `sendMessage` 重发
  - 最后一条是 assistant（已开始流式但中断）→ `regenerate()` 重生成

**验证**
- `curl /api/ai/chat -d '{"messages":[]}'` → 后端正确 emit `type: 'error'` chunk `Invalid prompt: messages must not be empty`
- `curl ... -d 'role=banana'` → emit `Unsupported role: banana`
- 两类 error chunk 都会被 useChat 转为 `error` state，触发 ErrorBanner

### 3. RAG threshold 0.30 → 0.40

**问题**：5/12 测试时观察到脱题 query「如何用 Rust 写一个 TCP 服务器？」会硬召回 1 条 sim 0.342 的噪声（人字桥工程图纸）。模型靠 system prompt 第 4 条扛住了，但不优雅 —— 前端 CitationStrip 仍会渲染那条无关史料。

**改动**
- [src/app/api/ai/chat/route.ts](../src/app/api/ai/chat/route.ts)：threshold 0.30 → **0.40**，注释说明决策原因
- [src/lib/ai/retrieve.ts](../src/lib/ai/retrieve.ts)：RetrieveOptions 默认值同步 0.30 → 0.40
- `scripts/smoke-retrieve.ts` 内部用 0.15 用于诊断，保留不动

**验证**

| 测试 | 旧 (0.30) | 新 (0.40) |
|---|---|---|
| 5 条正常 query smoke | 全召 | 全召（最低 sim 0.519） |
| 脱题 Rust 题 | sim 0.342 噪声硬召 1 条 | **0 hits** ✅ |
| 抗战 query top1 | 0.771 | 0.771 |

阈值上提没有伤及任何正常 query，且彻底杜绝了脱题噪声 → 模型直接走"暂无相关条目"分支，前端 CitationStrip 也不再误渲染。

## 四、踩坑与笔记

1. **朱砂 chip 不能用 `bg-accent` 系列**。Tailwind v4 + 项目 design token 里 `accent` = gold (`#a8884a`)，跟朱砂 (`#8b2e1f`) 是两个完全不同的色彩故事。HERO 已经用了金色作为黄金时代意象，再让卡片 hover 也染金就成了"金色乱炖"。换 cinnabar 立刻把"黄金时代 vs 档案登记"两套语言区分开。
2. **`text-[#f8f5ee]` 是项目内的"米色反白"约定**。AIChatClient 的"南"字徽和 user 消息泡也用这个色。Tailwind v4 任意值方括号写法工作正常，无需新增 token。
3. **AI SDK v6 `useChat` 返回的 `error` 是 `Error | undefined`**（不是 string）。直接 render 要走 `error.message`。`regenerate()` 不需要传 messageId 即可重生成最后一条 assistant；但若 error 在 user 消息发出后、assistant 流开始前发生（messages 末尾是 user），`regenerate` 行为不可靠 —— 我用 `messages[last].role` 分支，user → resend，assistant → regenerate。
4. **`createUIMessageStream` 的 `onError` 返回值会变成 client `error.message`**。后端是 `return err instanceof Error ? err.message : '生成失败'`，所以前端拿到的就是这个字符串。可在后端改成更友好的中文提示，但今晚保持原样（错误正文一般是 SDK 抛出的 "Invalid prompt: ..."、"Unsupported role: ..." 等，对开发期诊断有用）。
5. **threshold 调整的副作用范围**。改 retrieve.ts 的 default 也会影响其他调用方（目前只有 chat route 一个，但未来如果 cloud-tour / exhibition 也用 RAG，需注意默认值变化）。今晚没有其他调用方，安全。
6. **smoke-retrieve.ts 的内部 threshold 是 0.15 用于诊断**——故意用最松阈值看"召回的尾巴"是否合理，不要跟 production 阈值搅在一起。这个分离是有意的，今晚保留。
