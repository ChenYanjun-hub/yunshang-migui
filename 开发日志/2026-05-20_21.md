### 4. 站点 vs OSM 数据冲突的诚实暴露（5/21 关键决策）

诊断发现 **用户清单 29/34 站点经纬度 vs OSM 真实轨道偏差 5-77km**。最严重的：老范寨、大树塘、马街、南溪等南段站点偏 70-80km。

尝试过 3 种"修正"：

| 方案 | 做法 | 结果 |
|---|---|---|
| A. snap-to-line | 把每个站点投到 OSM 线上 | 用户拒绝 —— "数据真实性丢失" |
| B. 拉 OSM 真实站点节点 | Overpass `node[railway=station]` 替换 | Overpass 服务器多次 504/406，作罢 |
| C. Catmull-Rom 平滑曲线 | 让线穿过 34 个真实站点 | 让线错了（不是真实滇越东路）|

**最终决策（用户拍板）**：**两边都保留真实数据，让冲突暴露出来**。OSM 真实测绘轨道 + 用户清单真实站点 = 部分 marker 不完全贴线 = 数据考古的真实呈现。

演讲时把这变成卖点："**marker 跟线的偏差揭示了 1910 年法方测绘精度 vs 现代 GIS 的差距，是个有趣的考古发现，Phase 3 用 OSM railway=station 节点校准**"。

## 四、踩坑与笔记

1. **scp 不能假定"看到 100%"就真到位**。5/21 某次 scp 链中某文件实际没传（Mac 终端 && 链中断未察觉），后续 build 用的还是旧版，但浏览器表现"线走错了"让我以为是 OSM 数据问题。**经验**：scp 完一定要在服务器上 `wc -l` 或 `grep` 关键字确认目标文件特征，不能凭 scp 进度条 100%。

2. **OSM 数据的"真假"不能凭印象判断**。我看到 OSM 拉的数据跟用户清单不一致，直觉判断"OSM 错了"，做了一整套 Catmull-Rom 修复。用户对照论文配图后说"OSM 跟论文一致是对的"——我才意识到自己被用户清单"带偏"。**经验**：拉外部数据时，**永远以权威可对照源（论文/官方）为 ground truth**，不要让"项目内部数据"成为唯一参照。

3. **Leaflet z-index 不止 z-50 就够**。Tailwind 的 `z-50` = z-index: 50，但 Leaflet 内部 panes 是 200-700，控件是 1000。要盖 Leaflet 必须 `z-[1000]+`。**记录给未来**：用任何"自带 z-index"的组件库（Leaflet / Mapbox / videojs 等），周边 UI 默认 z-index 都要瞄它的上限再加。

4. **数据真实性 vs 视觉对齐的边界**。Phase 2 的 cloud-tour 让我经历了完整一轮"为了对齐而扭曲数据"的诱惑：
   - 第一次 snap stations 到 OSM 线 → 站点假了
   - 第二次 Catmull-Rom 让线穿站点 → 线假了
   - 用户两次都否决："**不能为了表达丧失真实性**"
   
   最终领悟：**演示 ≠ 编造一致性。真实数据的"不完美"比假精确更有说服力**。让冲突暴露，再用"考古差异"作为产品故事讲出来，反而是 Phase 3 的天然 backlog。

5. **国际网络服务的不可控性要内化进选型**。Overpass API 5/21 多次 504/406；Google Fonts 在中国本地 build 失败；Vercel 在国内访问不稳。每条都不可控、不可预测。**应对范式**：能内置就内置（字体本地子集化）、能预下载就预下载（Overpass 数据 commit 进 repo）、能换国内就换（部署在阿里云）。

6. **决策点要写下来，否则会反复**。今晚一度想把昨天的"用 OSM 真实主线"决策推翻（因为 snap 失败），幸亏 docs/Decision-Notes.md 里 #12 已经写清楚"演示场景，零外部依赖 > 最佳工程实践"。看一眼立刻平息了内心的折腾。**Decision Notes 不是文档负担，是给未来自己的安全带**。
