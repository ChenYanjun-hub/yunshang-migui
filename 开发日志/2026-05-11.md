## 四、踩坑与笔记

1. **DashScope batch 上限是 10，不是 25**。OpenAI 兼容模式的 `/embeddings` endpoint 拒绝 11+ 的 batch："batch size is invalid, it should not be larger than 10"。
2. **`server-only` 包不在 deps 里**。`embed.ts` 第一版加了 `import 'server-only'` 防御，结果 `node + tsx` 跑脚本时找不到模块。删掉即可 —— `DASHSCOPE_API_KEY` 没有 `NEXT_PUBLIC_` 前缀本就不会进客户端 bundle，不需要这道哨兵。
3. **`NEXT_PUBLIC_` 前缀的致命陷阱**。任何 `NEXT_PUBLIC_*` 环境变量都会在 build 时被字面替换进客户端 JS。给 service_role key 加这个前缀 = 暴露数据库 root 权限给所有浏览器访问者。
4. **AI SDK v6 自定义 data parts 形如 `type: 'data-<name>'`**。chunk shape: `{ type: 'data-citations', data: [...], id?, transient? }`。`transient: true` 不进 `message.parts`，`transient: false`（默认）持久化。Client 侧 `message.parts.filter(p => p.type === 'data-citations')`。
5. **`createUIMessageStream + writer.merge` 模式**。这是 v6 在文本流中插入自定义 data part 的官方手法。execute 函数里先 `writer.write` 自定义 chunk，再 `writer.merge(streamText().toUIMessageStream())` 合并 LLM 输出。注意是 `toUIMessageStream()` 而**不是** `toUIMessageStreamResponse()`（后者返回 Response，前者返回 ReadableStream）。
6. **`useSearchParams` 客户端组件需要父侧 `<Suspense>` 包裹**。否则 Next.js 16 build 会报 "useSearchParams should be wrapped in a suspense boundary"，dev 也会有 warning。
7. **service-role 直连写需自建 supabase-js client**，不要用项目里的 `@/lib/supabase/server`（那是 SSR cookie 模式，权限 = 当前登录用户）。
8. **Supabase ON DELETE CASCADE 在演示中非常好用**：admin 删 archive → 关联向量自动消失，零额外代码。
9. **种子数据重复别在 retrieve 层 patch**。当时差点加 SQL `DISTINCT ON (title)` 把它盖掉 —— 那是错的，应该清在源头：脏数据留下来，未来会有第三处、第四处遭殃。

## 七、决议：Admin 上传 PDF 与 RAG 同步的方向

**今晚不做。未来按下方方向走（已锁定，未来开做时直接对照）**

用户提问："未来支持上传 PDF 时，史料藏馆和 RAG 是否做成两个独立的东西，每次上传两边手动同步？"

**最终采纳的方案 C：双轨架构 + archive_id 串联**

| 层 | 职责 |
|---|---|
| 展示层（archives 表） | 元信息 + 封面图（PDF 自动取第 1 页生成）—— 卡片墙 / Lightbox 的 UX 保持图像中心 |
| 检索层（archives_embeddings 表 v2） | PDF 文本切片 N 条 —— RAG 索引 |
| 串联 | 双表通过 `archive_id` 关联；citation 卡片点击 → `/archive?open=<id>&page=<n>` → Lightbox 内 PDF 预览滚到对应页 |

**未来开做时的改动清单**（写在这里方便未来 Claude / 自己直接对照）：

1. **DB schema**
   - 新增 `archives.attachment_url` / `archives.attachment_type` 字段
   - `archives_embeddings` 主键改为 `(archive_id, chunk_index)`，加 `chunk_index int` 和 `page_no int`
   - migration 名建议 `002_embeddings_multi_chunk.sql`，**注意为现有 6 条 archive 添加 `chunk_index = 0` 兼容**
2. **ImageUpload 组件**升级为 `MediaUpload`，accept `image/* + application/pdf`；后端 PDF 自动提取第 1 页生成封面
3. **`embedAndUpsertArchive`** 改写为 `embedAndUpsertArchiveChunks`：先 `.delete().eq('archive_id', id)` 清旧 chunks → 切分 + batch embed → batch upsert
4. **`match_archives` SQL 函数**：返回时按 `archive_id` 去重 / 合并最高 chunk，避免单个长 PDF 占满 topK
5. **citation 卡片**识别 chunk 的 `page_no` 字段，跳 `/archive?open=<id>&page=<n>`；Lightbox 加 PDF 预览组件（pdf.js）

**不变量**（今晚立下、未来必须延续）：
- `archive_id` 保持唯一稳定主键
- ON DELETE CASCADE 保持
- archive 表的 image_urls / cover_url / description 字段保留
